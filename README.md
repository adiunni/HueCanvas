# HueCanvas
A local album-art-driven lighting dashboard for two color Hue bulbs and two warm-white bulbs. Python 3.11+; mock mode is the default. This repository itself is the project root—no extra huecanvas folder is needed.

## Setup and run
```sh
cd /Users/adiunni/Github/HueCanvas
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
cp .env.example .env
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```
For subsequent launches, run `./start.sh` or double-click **start.command** in Finder. The launcher uses this folder's `.venv`, creates it before installing packages if it is missing, and installs dependencies if HueCanvas or Uvicorn is not installed. You do not need to activate the environment. Press Ctrl+C in its Terminal window to stop the server. To use another port, run `PORT=8001 ./start.sh`.

Open http://127.0.0.1:8000. Upload a PNG/JPEG (maximum 10 MB); its palette automatically starts the mock lighting engine. Edit swatches, select a mode, and set brightness, white fill, cycle speed and transitions. Controls are responsive on mobile. The optional web fonts fall back to system fonts offline.


## Behavior
Four mock lights have explicit roles. Real lights are initially disabled and unassigned: choose exactly your four bulbs and assign roles. Other discovered lights remain untouched. Capability detection comes from v2 light resource fields. Warm-white bulbs never receive XY color. Color-temperature capability is reported, but this MVP leaves temperature unchanged. Names/roles/enabled choices persist in `.huecanvas/lights.json`; renaming is local to HueCanvas.

Start captures the enabled bulbs' actual pre-session state. Pause and Stop hold the current appearance; Restore writes the captured on/off, brightness and XY state. Disable a light to exclude subsequent animation commands. Identify invokes Hue's native identify action (simulated acknowledgment in mock mode).

The ambient looks (Static, Crossfade, Rotate, Breathe) use album colors at a fixed relaxed pace: a 15-second cycle with 3-second transitions. These are no longer adjustable in the dashboard. Ordinary REST animation frames occur at most once every two seconds, and each bridge request is spaced at least 250 ms apart. Transitions are at least one second. Transient transport errors retry connection once; animation failures back off to 30 seconds. The dashboard reports errors. REST preview is an illustration using the palette, not measured bulb output or an accurate colorimetric simulation.

## Connect real Hue hardware
For the requested local setup, only the bridge LAN IP and its application key are needed:

```dotenv
MOCK_MODE=false
HUE_BRIDGE_IP=192.168.1.2
HUE_APPLICATION_KEY=your_generated_username
```

Restart the server after editing `.env`. Local bridge requests use HTTPS with certificate verification disabled by default (`HUE_TLS_VERIFY=false`). HTTPS still encrypts traffic, but this mode does not authenticate the bridge certificate. This policy applies only to private LAN bridge addresses; public discovery continues to use verified HTTPS.

The IP field accepts a bare IP, `IP:443`, or `https://IP:443`. The app sends the key in the `hue-application-key` header to `/clip/v2/resource/device/` and `/clip/v2/resource/light`. Existing `HUE_BRIDGE_ID` and `HUE_CA_CERT` settings are ignored in this local mode, so the PEM file is optional.

Use the `username` returned by `POST /api` as `HUE_APPLICATION_KEY`. The separate `clientkey` is for Entertainment streaming and is not needed for REST control. The pairing label `hue_canvas` is valid and does not need to match any later request. The JSON field is lowercase `devicetype`, for example `{"devicetype":"hue_canvas"}` ([official pairing guide](https://developers.meethue.com/develop/get-started-2/)). No new pairing is needed if you already have a working application key.

If you have no key, press the physical bridge button and click Pair with the bridge IP filled in. HueCanvas uses that same `hue_canvas` label and saves the returned application key in `.huecanvas/credentials.json` with mode 0600. The file and `.env` are ignored by Git.

Assign COLOR_LEFT/RIGHT to the two color bulbs and WHITE_LEFT/RIGHT to the warm-white bulbs; select **Enable bulb** for only those four lights. Clear a role before reassigning it.

### Optional verified TLS
To verify the bridge certificate instead, set:
```dotenv
HUE_TLS_VERIFY=true
HUE_BRIDGE_ID=your_16_character_bridge_id
HUE_CA_CERT=hue.pem
```
Use a trusted Hue CA from the official [HTTPS guidance](https://developers.meethue.com/develop/application-design-guidance/using-https/) (developer login may be required). Relative PEM paths resolve from the project root. Verified mode checks the certificate chain and bridge identity, and fails closed on verification errors; it never falls back to unverified TLS.

Bind to loopback. This local tool has no user authentication and is not intended to be exposed to the internet. Cross-origin browser writes are rejected.

## Optional macOS Music
Set `APPLE_MUSIC_ENABLED=true` and restart. Grant macOS Automation access for Music/System Events when requested. Track identity is checked on a half-second cadence using Music's persistent ID and metadata. A track change updates the title, cancels unfinished artwork work for the old track, and starts loading the new cover. Artwork is delivered through live events before palette extraction completes, so clustering and the ordinary dashboard poll no longer delay the cover. Tracks on the same album can have different artwork and are checked separately.

Raw covers are cached on disk by track identity; palettes are cached by artwork hash. Missing/downloading covers retry after two seconds. Export verifies the expected track ID, preventing an old request from reading a newer track's cover. Apple Music may still delay metadata or artwork availability; this is near-immediate delivery once Music provides the image, not zero-latency track detection. PNG/JPEG covers are preserved and other image formats are normalized. Manual upload stays available.

A new track clears the old audio tempo/drop history. Percussion effects continue responding to new attacks while BPM collects a fresh window. This integration follows Apple Music, not Spotify or browser artwork.

## Optional rekordbox with two decks (DDJ-FLX4)
Set `REKORDBOX_ENABLED=true` and restart with `./start.sh`, which installs the `rekordbox` extra (`pyrekordbox`, `sqlcipher3-wheels` and `python-rtmidi`) on first use. Manual install: `.venv/bin/python -m pip install -e '.[rekordbox]'`. rekordbox takes precedence when both sources are enabled. Run rekordbox on the same Mac as HueCanvas, with the controller connected.

**Which track:** rekordbox has no scripting interface. HueCanvas therefore reads its **play history** from `~/Library/Pioneer/rekordbox/master.db` (override with `REKORDBOX_DB`) twice a second, through a read-only SQLCipher connection, and never writes to your library. rekordbox adds a track to history only after a deck has played it for the **Playback time** set in *Preferences → Advanced → Browse* (rekordbox 6.6.8+; often 30–60 s by default). Lower it so tracks are identified sooner. At 1 s, rekordbox logged tracks one to two seconds after they started on the FLX4, so HueCanvas identifies them almost immediately; very low values also log tracks you only cue briefly with the deck playing. Artwork is copied from rekordbox's `share/PIONEER/Artwork` folder. History older than 30 minutes is ignored at startup.

**Which song is on each deck:** rekordbox never records which track is loaded on which deck, and it exposes nothing else internally: it reads audio files in a fraction of a second and closes them, sends no Pro DJ Link traffic in Performance mode, and its local helper connection carries no track data. HueCanvas therefore matches each history row to the deck you pressed just before it. With Playback time at 1 s, rekordbox wrote every row about a second after the PLAY or hot cue press that started the track. A row goes to a deck you LOADed since it was last identified, choosing the PLAY or hot cue press closest to one Playback time before the row was written, within four seconds. That covers a PLAY that rekordbox ignored because the track was still loading, followed by a hot cue that started it. A LOADed deck that was started with the mouse takes the row next. A press on an already identified deck counts only when nothing was loaded, as when you load with the mouse. When there is no evidence at all, the row is not attributed to either deck. Deck assignments are saved in `.huecanvas/decks.json` and restored when HueCanvas restarts while the same rekordbox process keeps running. After rekordbox itself restarts, each deck is identified at its next load.

**Which deck is live:** history has no deck number. HueCanvas therefore also listens to the controller's MIDI (`REKORDBOX_CONTROLLER`, default `DDJ-FLX4`; empty disables). macOS shares the controller between rekordbox and HueCanvas, and HueCanvas only reads its messages, except for one Pioneer position query at connect, which rekordbox also sends.
- **Volume:** each deck's level is channel fader² × a constant-power crossfader curve (deck 1 left, deck 2 right). The louder deck is live. A challenger must lead by 5% for one second, or 0.25 s when the live deck is silent, as on a fader cut. Equal volume keeps the current deck. Trim and EQ are not counted.
- **LOAD, PLAY and hot cues:** LOAD clears a deck's track. A loaded deck that is not live stays silent until PLAY, a hot cue pad (pads 1–8 in hot cue mode) or its history row arrives, so a cued deck never takes over. LOAD onto the audible live deck keeps it audible while it waits for the new track's history row.
- **Attribution:** HueCanvas reads Playback time from rekordbox's settings and matches rows to presses as described above. Tracks both loaded and started with the mouse go to the deck identified longest ago, since decks alternate. A logged track's deck counts as playing.
- **Switching:** when the crossfade or faders hand over to a deck whose track is known, the title, artwork, palette and lights switch at once, and the cover comes from cache. If rekordbox logs the incoming track while you are still cueing it, the switch happens during the transition itself. Otherwise the previous track's lights stay until rekordbox logs the new one.
- **Startup:** fader positions are unknown until each control moves (untouched counts as up), so move the crossfader once after starting. Until any controller message arrives, the newest history row is used.

The **Album** card shows both decks side by side as square covers, each with title, artist and a volume bar, plus the crossfader position. The live deck, the one the lights follow, is outlined and marked LIVE. A status line beneath reports permission, controller or history problems. The play state of a deck is inferred only from LOAD, PLAY, hot cues and history rows, because rekordbox's own deck state is not readable. A deck that stops at the end of a track with its fader up still counts as audible.

## Extension boundaries
`app/hue/entertainment.py` implements HueStream v2 XY/brightness frames over DTLS 1.2 PSK, using OpenSSL through `ctypes`. Beat effects stream at 20 fps to the enabled color bulbs only. Warm-white lamps default to a slower music-driven brightness response over REST, or optional steady fill. Their worker runs separately from the color stream. MIDI clock, Ableton Link and direct controller (MIDI) triggers remain future adapters; rekordbox track changes come from its play history (see above).

## Troubleshooting real lights
- Stop the previous server with Ctrl+C and restart after changing `.env`. The dashboard must show **LIVE HUE**, not **SIMULATION**. Only one process can listen on port 8000.
- An empty `HUE_APPLICATION_KEY` requires physical-button pairing in the dashboard. A bridge ID is not an application key. A generated key is saved to `.huecanvas/credentials.json`.
- Select **Enable bulb** for your four bulbs. Real bulbs start disabled. Start now reports an error if none are enabled.
- If the bridge is unreachable, check that it is powered and the Mac shares its LAN; check VPN routing and System Settings → Privacy & Security → Local Network for the app launching the server. Discovery can identify a bridge even when direct LAN access is blocked.
- Run `.venv/bin/python examples/check_bridge.py` from the same terminal used to launch the server for a read-only device-endpoint and authentication check. The diagnostic does not print keys or change lights.

## Browser requests and the Hue application key
The browser sends control requests to FastAPI on localhost (for example `POST /api/control/start`). Python then sends bridge requests such as `PUT https://<bridge_ip>/clip/v2/resource/light/<light_id>` with the `hue-application-key` header loaded from `.env`. That header is set on the shared HTTPX client in `app/hue/client.py`, so it is attached to device discovery, light discovery and light updates.

Browser DevTools only shows the browser-to-FastAPI requests. It cannot display the separate Python-to-bridge requests. The key is kept on the server and is not returned in state responses or embedded in frontend JavaScript. The diagnostic script tests the authenticated bridge endpoint from Python without printing the key.

## Automatic BPM and beat effects
1. In **Audio MIDI Setup**, create a **Multi-Output Device** containing your speakers/headphones and **BlackHole 2ch**. Select it as the Mac sound output, so Music audio reaches both your speakers and BlackHole. Follow the driver's [official multi-output setup](https://github.com/ExistentialAudio/BlackHole/wiki/Multi-Output-Device). HueCanvas does not change system audio routing automatically.
2. Keep the matching `HUE_APPLICATION_KEY` and `HUE_CLIENT_KEY` in `.env`. `HUE_CLIENT_KEY` is the `clientkey` from the same `POST /api` response, generated with `{"devicetype":"hue_canvas","generateclientkey":true}`. A working application key alone is enough for REST, but DTLS streaming needs both keys. Restart after editing `.env`.
3. Create an Entertainment area in the Hue app with exactly the two color bulbs. HueCanvas automatically selects a matching inactive area (your **Music area** is compatible). Stop other Hue Sync applications before using it. `HUE_ENTERTAINMENT_AREA` can select a specific area's UUID.
4. In HueCanvas, choose **Lighting → Music → Pulse**, **Flash** or **Brightness only**, then press **Start**. Start also begins listening, on the input you last used or else on the BlackHole loopback input; if none exists, **Setup** opens with the routing controls. Allow audio-input access for the launching app if macOS requests it. No recording is saved; analysis keeps at most 20 seconds in memory. Ambient looks never start capture themselves. **Restore** ends playback and stops listening; Pause and Stop keep listening so the tempo stays locked.

The dashboard only shows settings that apply to the current choices. For Pulse and Flash, **Pulses follow** chooses **Beat** (the tempo clock), **Beat + drums** (the tempo clock locked to the kicks, see below), **Drums** (hits, rolls and drops), **Kick, or snares** (mids when the kick drops out) or **Levels** (bass/mid volume thresholds). Choosing Beat + drums, Drums or Kick-or-snares turns on **Ignore melody and bass notes** (drum stems) by default. **Pulse every** selects every beat/hit, every 2nd or every 4th. Ordinary sharp flashes are capped at three per second; confirmed rolls can follow attacks up to **Fastest roll flashes · per second** (default eight).

**Color lights** and **White lights** are configured separately. Color lights: **Brightness**, **Low point between pulses**, **Pattern → Together / Alternate**, and **Colors → Cycle album colors / Keep each bulb's color** with **Next color every**. White lights: **Behavior → Follow the music / Steady**, **Brightness**, and, while following music, their own **Low point** and **Pattern**.

### Beat + drums
**Pulses follow → Beat + drums** pulses on every beat of the detected tempo, so pulses keep going through missed hits, fills and breakdowns, unlike **Drums**. Each detected kick near a predicted beat pulls the clock 35% of the way onto it; snares and claps pull 15%. Hi-hats and hits more than 20% of a beat away from the clock are ignored, so off-beat snares do not drag it. Corrections are fractions of the error, so the clock converges smoothly rather than jumping: from 60 ms off, it is within 6 ms by the fourth kick and within 3 ms from the sixth. Once the clock is within 6% of a beat, a small tempo trim (at most ±3%) is also learned, which absorbs a detector reading such as 127.4 for a 128 BPM record. Trim changes keep the current beat where it is. If four kicks in a row agree with each other but miss the clock, for example when the detector picked the off-beat, the clock moves onto them at once.

The clock learns how far the detector's beat usually sits from the drums. After eight beats without kicks it follows the detector's phase, corrected by that offset, so a nudged record is followed and returning drums land on the pulse. Until a tempo locks, pulses follow drum hits, as in **Beat**. Confirmed snare rolls add their faster flashes on top of the steady pulse, and drop accents apply as usual. **Pulse every**, **Pattern**, **Timing → Delay lights** and the drum sensitivity settings apply.

In a two-minute synthetic 128 BPM simulation, the detector's beat estimate jittered by ±15 ms each second, 30% of kicks went undetected, detected kicks were ±5 ms off, and there were two breakdowns. Beat + drums averaged 1.5–1.9 ms from the drums (worst 5–10 ms) across three runs, against 19–22 ms (worst 35 ms) for the detector clock alone. Drums alone left 112–121 of 256 beats without a pulse. These are synthetic numbers; check the feel with your own tracks.

### Tempo detection
The tempo is detected automatically, as in DJ software. Each second, the last 6–20 seconds of audio become an onset envelope from three bands (30–200 Hz, 200 Hz–2 kHz, 2–12 kHz). That envelope is folded at every candidate beat period from 55 to 512 BPM, measuring how strongly hits line up on the beat ("pulse-train" scoring). Related tempos (double, half, 3:2, 4:3) are compared with a soft preference for tempos around 120 BPM. Below 80 BPM, regular activity between the beats (hats, ghost notes) indicates a half-time feel over a faster beat, so dubstep and trap read at 140–145 rather than 70; a bare pulse stays as it is. Estimates pass through a tracker that shows the median of recent windows. It ignores a single window at a related tempo, replaces the tempo after three agreeing windows when the song changes, and snaps to a whole BPM once stable. The Lighting panel and header show the tempo and whether it is **Locked**. **½** and **×2** correct a double/half reading for the current song (reset on the next track), and **Set tempo manually** overrides detection. Until a tempo locks, Beat pulses follow drum hits instead of waiting.

Tempos from 30 to **512 BPM** can be set manually or reached with ×2: 512 is a 1/16-note loop roll on a 128 BPM track (four hits per beat). Detection keeps reporting the track's own tempo during a loop roll or over dense 1/16 hi-hats, as DJ software does, so the beat grid does not jump; a sustained 1/16 roll on a 128 BPM track still reads 128. Fast tempos do not raise the light-rate limits: ordinary Flash pulses stay at three per second or fewer (a 512 BPM clock flashes every third beat), and Pulse swells stay at four per second or fewer, which is about what the 20 fps stream can draw smoothly. To follow the hits of a roll itself, use **Pulses follow → Drums**; confirmed rolls flash up to **Fastest roll flashes · per second** (eight per second is 480 per minute).

On a synthetic set of genre loops with bass and chords (house 124, techno 132, trance 138, hip-hop 90 with and without swing, DnB 174, dubstep 140, pop 100, rock 120, reggaeton 96, trap 145), the detector found 10 of 11 tempos within 1 BPM from 6–12 seconds of audio and all 11 from 20 seconds; the previous detector found 5 of 11. Drum and bass reads as 87 until about 20 seconds; use ×2 if it does. Slow songs below 80 BPM with steady hi-hats read at double tempo, as in DJ software's default ranges; use ½. These results are from synthetic audio, not recorded songs. While listening, two seconds of sustained silence (after the one-second audio energy window drains) restore the enabled bulbs to their pre-Start on/off, brightness and XY state and release the Entertainment area. Capture stays active and playback resumes after sustained audio returns; Beat pulses follow drum hits until the tempo locks again. Short gaps keep playing, and gaps between percussion attacks stay at the pulse floor until the silence timeout. Manual playback without audio capture continues normally. Stop listening pauses an audio-driven streaming effect, including percussion triggers even when Manual BPM is selected. Pause, Stop and Restore release the Entertainment area; Restore also returns the original bulb state.

OpenSSL with DTLS-PSK support must be available. On this Mac, `/opt/homebrew/opt/openssl@3/lib/libssl.3.dylib` is used; another installation can be supplied with `HUE_OPENSSL_LIB`. Credentials stay in process memory and are not passed as shell arguments. Cloud discovery certificate verification is unchanged.

## Live spectrum and color preview
Open **See the sound** and click **Listen to BlackHole**, or press Start on a music look. Play music through your configured Multi-Output Device. The frequency graph appears within a short audio window, without waiting for a BPM estimate. Starting capture does not start a lighting effect.

The graph spans 20 Hz–20 kHz, limited by the input sample rate, on a logarithmic frequency axis with a fixed −90 to 0 dBFS amplitude scale. Bass (20–250 Hz), midrange (250 Hz–2 kHz), and treble (2–20 kHz) cards show integrated band RMS levels; bars show peak amplitudes, so their dB values can differ. The strongest frequency is shown above the preview. Silence and stalled capture clear the visual rather than holding an old spectrum.

Choose **From the album palette** to color the bands from the current artwork, or edit the three band swatches to try your own mapping. The **Live color blend** combines those colors in proportion to band RMS and dims with input volume. These are local visual preview controls; they do not send color changes to the bridge. The spectrum shows mixed frequencies rather than separated instruments, so a band may include drums, vocals, and other sounds.

The spectrum shares the existing explicitly started input stream and sends only derived levels to the browser. FFT analysis runs outside the audio callback and lighting loop. The graph refreshes up to ten times per second; hidden tabs stop requesting updates. No raw audio is saved or sent to the browser. Stop listening ends capture and clears the graph.

## Frequency levels with bass priority
Choose **Pulse** or **Flash**, then **Pulses follow → Levels**, and click **Start**. No BPM estimate is required. Together/Staggered, palette cycling, pulse division, and timing delay apply to these crossings too. White bulbs keep their slower music-brightness worker.

Defaults implement the requested strict comparisons:
- Bass **above −15 dBFS** creates a pulse.
- If bass is **below −70 dBFS**, mids **above −20 dBFS** can create a pulse.
- Between −70 and −15 dBFS bass blocks mids and neither band creates a pulse. Exactly −70 dBFS does not enable mids; equality at a trigger threshold does not fire.

All three levels appear under Levels; bass fallback must remain below the bass trigger. A band fires once on entry above its threshold and rearms when it falls at least 2 dB below its trigger. A sustained note therefore does not generate repeated flashes. If mids were already loud while blocked by bass, their first eligible crossing can fire when bass falls below the fallback. Sharp flashes retain the three-per-second cap; gentle pulses retain their smooth decay and stagger.

Thresholds compare **band RMS**, matching the spectrum cards (bass 20–250 Hz; mids 250 Hz–2 kHz), rather than a single spectrum bar's peak amplitude. The detector uses the same calibrated 8192-sample Hann window, updated every 10 ms once full. At 48 kHz this spans approximately 171 ms; its smoothing, plus capture and bridge latency, can delay responses compared with the percussion onset trigger. Absolute dBFS levels depend on the player's volume and mix. Use the spectrum cards and live gate readout to tune values for your music. Spectrum previews remain independent of actual palette settings.

This level gate is separate from **Drums**, which detects spectral changes and broadband attacks, and from **Accent drops**, which requires a sustained energy lift with percussion. Crossing −15 dBFS alone is not evidence of a musical drop. Drop accents remain controlled by the existing drop setting.

## Drums, percussion, and drop accents
Choose **Pulse** or **Flash** and set **Pulses follow → Drums**. No stable BPM estimate is needed to start. The detector compares consecutive audio slices in four bands: low (40–180 Hz), body (180 Hz–1 kHz), crack (1–4 kHz), and air (4–12 kHz, limited by the input sample rate). Changes in each band are compared with their own recent background, so a loud bass bed does not set the threshold for a quieter snare. Neighboring frequency bins help suppress false attacks from a held note's vibrato. This uses the multiband spectral-change approach described in [librosa's onset documentation](https://librosa.org/doc/0.11.0/generated/librosa.onset.onset_strength.html), implemented with the existing NumPy dependency.

**Sensitivity** changes how large a band change must be to count as an attack. It applies directly to detection, without a second sensitivity filter discarding already-qualified attacks. Drum labels are approximate: these are kick-like, snare-like, and high-percussion transients in a mixed signal. Other transient sounds can resemble drums, and masked or quiet attacks can still be missed.

**Ignore melody and bass notes** (drum stems, on by default) stops pulses on melody, chord, bass-line and vocal notes. Each detected attack waits for a streaming drum stem before it becomes a pulse. The stem uses harmonic–percussive separation by median filtering (D. FitzGerald, “Harmonic/Percussive Separation using Median Filtering”, DAFx 2010): over a 21 ms window, steady tones are separated from energy that is smooth across frequency. A snare, clap or hat counts when at least 35% of its new energy above 1 kHz is percussive and it noticeably lifts that band. A kick's body is a low tone, so kicks are recognised by a low-dominant energy jump whose pitch falls on every 10 ms hop, or by a strongly percussive click when the kick lands on a new bass note. Confirmation adds about 50 ms (55–60 ms with typical audio buffers); pulse timestamps stay on the attack, and sharp flashes keep their full width when confirmed late. Increase **Timing → Delay lights** only if your speakers play later than this. Unchecking it keeps the faster behaviour, roughly 15 ms after the attack, including note attacks.

DJ applications separate stems with neural networks; that needs a large model and much more audio context than a 20 fps light stream allows, so HueCanvas uses this signal-processing approximation. On a synthetic test set (piano, plucks, chord stabs, pads, saw and sub bass lines, a vibrato voice), isolation reduced pulses on notes from 327 to 8, removed every note pulse from drums-plus-notes mixes, and kept 67–100% of drum hits depending on how dense the mix was. Known gaps: dense saw chords whose harmonics are closer than about 90 Hz above 1 kHz can still look percussive; a kick that starts exactly with a new bass note and has no click can be missed; and hits that coincide with a loud note onset are sometimes dropped. These numbers come from synthetic audio, not recorded songs.

Four closely spaced attacks with a similar frequency profile form a roll candidate. Intervals and profile similarity must remain consistent; gradual acceleration is supported. Together pulses all color bulbs; Staggered advances through the enabled color bulbs. Gentle roll pulses shorten their decay to reveal successive hits. In Flash, confirmed rolls use the **Fastest roll flashes · per second** control (3–8, default **8**); ordinary attacks, frequency thresholds, and BPM-clock flashes retain their three-per-second cap. Pulse every still selects every 1, 2, or 4 accepted attacks. Rapid rolls are thinned when needed, short high intervals preserve visible low frames, and flashes stop when detected attacks stop. The 20 fps stream and hardware latency limit exact synchronization. White bulbs retain their slower music brightness changes.

**Pulses follow → Kick, or snares** pulses on sudden changes in one frequency band, using the same per-band comparison. With drum isolation on, bass changes are confirmed kicks and mids changes are other confirmed drums, so bass lines and synth notes no longer drive it. Bass (40–180 Hz) leads while it keeps producing attacks; a decaying kick or low-frequency leakage from snares does not retrigger it. When bass stops (a bass-less drop, a filtered build-up, or a breakdown) and the mids (180 Hz–4 kHz) keep changing, the mids take over about one missed bass attack later. Bass reclaims the lead after two fresh attacks. A confirmed drop chooses its band directly: if the bass band did not lift, the mids drive the lights for at least two seconds. Mid-band changes during a snare roll keep the roll flash limit. The live spectrum's rhythm readout shows which band the lights are following. ## White lamps and brightness-only music
Your two LWA025 Hue White bulbs expose dimming but no Entertainment renderer service. Brightness is supported; fast Entertainment streaming is not. Hue also advises against continuous fast updates over the [REST API](https://developers.meethue.com/new-hue-api/), so the white lamps use a slower music envelope.

Select **Music → Brightness only** to make every enabled dimmable bulb change brightness while preserving its existing color and color temperature. This mode uses only the bridge IP and application key; no Entertainment area or client key is required. Start begins listening; the tempo is detected automatically, or use **Set tempo manually**. **Color lights → Brightness** and **Low point between pulses** set the color bulbs' range; **White lights → Brightness** and **Low point** set the whites' range independently.

**White lights → Behavior → Follow the music** (the default) applies in every look while HueCanvas is listening, including Static, Crossfade and Rotate; ambient looks follow music only if listening was started from See the sound or Setup. Select **Steady** to hold the whites steady instead. **Pattern → Alternate** offsets the two whites over beat groups, independently of the color bulbs' pattern. When BPM is available, the REST envelope alternates high and low over whole groups of beats: at 120 BPM it changes target every four beats (two seconds). At other tempos, whole beat groups keep the interval at least two seconds. Without an audio BPM estimate, brightness follows recent audio energy. ## BlackHole shows zero or cannot find a beat
BlackHole receives audio only when the player sends output to it. HueCanvas now checks the Mac's actual default output and the active members of aggregate devices. A device merely named Multi-Output is not enough: it must include BlackHole and speakers/headphones, and it must be selected for sound output. Click **Use Multi-Output for Mac sound** to select an existing compatible device. This explicit action changes the Mac sound output; opening HueCanvas or starting capture does not change routing automatically. **Check routing** refreshes the diagnosis.

The input panel now distinguishes:
- **Not listening:** press Start on a music look, or Listen now in Setup; launching the server does not begin capture.
- **Frames arriving, input silent:** play music and check its output route. Zero input is not a BPM-estimator failure.
- **Capture stalled:** no callbacks are arriving; restart listening and check permissions or device availability.
- **Audio present, no steady beat:** the sound reaches HueCanvas but has no reliable tempo yet. Beat pulses follow drum hits meanwhile; drum and level triggers work without a tempo, or use Set tempo manually.
- **Processing/open error:** the error remains visible; Restart listening can reopen capture without restarting the whole server.

Raw input level in dBFS, per-channel levels and received-frame counts are exposed in audio status. Analysis uses the stronger stereo channel with hysteresis, preserving sound from one-sided or opposite-polarity stereo sources that averaging could cancel. Silence is diagnosed within about half a second; the first tempo needs six seconds of usable audio. Callback errors are surfaced rather than silently leaving a stream that appears active.

If using rekordbox or another DJ app, its selected output may override macOS: select the compatible Multi-Output Device in that app, or send a dedicated output to BlackHole. An aggregate containing only speakers does not feed BlackHole. Follow the driver's [official setup](https://github.com/ExistentialAudio/BlackHole/wiki/Multi-Output-Device) for device ordering, clock source and drift correction if playback itself stalls.
